> **面向 AI 代理的工作者：** 必需子技能：使用 superpowers:subagent-driven-development（推荐）或 superpowers:executing-plans 逐任务实现此计划。步骤使用复选框（`- [ ]`）语法来跟踪进度。

**目标：** 在不破坏 0.3.0 捕获、自动保存、搜索、WikiLink、导出和备份闭环的前提下，将 2notes 升级为以稳定块 ID 为底座的结构化本地知识库，并依次交付主窗新建、文档层级与大纲、知识健康和 Markdown 导入。

## 2. 决策与方案比较

用户已确认：本轮只产出方案；下一阶段正式进入块模型；范围包含主窗新建、层级组织、知识健康、Markdown 导入；长期保留块级引用、图谱和 AI 只读接口。

第二轮问题未提交答案，本计划采用推荐默认值：SQLite 是唯一权威内容源；首版是结构化轻编辑器；0.4.x 保留一次迁移前正文快照；层级先做文档父子关系和标题大纲。

### 方案 A：应用块文档真源 + blocks 查询投影（采用）

- `entry_documents.document_json` 保存完整结构和稳定 ID。
- `blocks` 保存扁平投影，服务大纲、未来块引用和诊断，可从 JSON 重建。
- `entries.current_content` 保存派生 Markdown，现有 FTS、WikiLink 和导出先继续工作。
- 优点：事务清晰、编辑器可替换、迁移风险最低。
- 代价：0.4.x 有三种表示，必须只允许后端在一次事务内生成后两者。

### 方案 B：blocks 行表直接作为真源（不采用）

SQL 查询直接，但 marks、列表、粘贴和批量保存需要大量细粒度 SQL，从行重组编辑器文档复杂，首版收益不足。

### 方案 C：Markdown / JSON 文件真源（不采用）

可移植性好，但需要文件监听、原子写、冲突检测、路径变更和备份重构，与 SQLite 单真相源承诺冲突。

### 架构原则

- Tiptap JSON 不是持久化契约；`tiptapAdapter.ts` 必须转换为应用 `BlockDocument`。
- 前端不得提交 `plainText`、`markdownText` 或 blocks 投影，这些值由 Rust 生成。
- 0.4.x 发布构建不允许业务代码直接更新 `entries.current_content`，只能调用 document repo。schema 005 到聚合切换期间仅允许开发分支短暂兼容，且不得产出安装包。
- 任务 4–6 的 `currentContent` 兼容写路径只有在 checksum 变化时才从纯文本重建 document；纯文本无法保留既有 block UUID，因此这一内部窗口不承诺 ID 稳定。稳定 block ID 的验收从任务 7 删除兼容输入后开始。
- `revision` 属于 entry 聚合根，一次文档保存只增加一次；`entry_documents.entry_revision` 用于检测迁移窗口内的旧文本新写入。
- 至少包含一个空 paragraph 的文档是合法内容。主窗新建可创建语义空文档；块编辑器允许用户清空正文；快速捕获仍在 command 边界拒绝空白纯文本。
- 快速捕获仍接受纯文本，后端创建初始块文档；快速窗口不加载富编辑器。

## 3. 领域模型

```rust
pub struct BlockDocument {
    pub schema_version: u32,
    pub blocks: Vec<BlockNode>,
}

pub struct BlockNode {
    pub id: String,
    pub kind: BlockKind,
    pub attrs: BlockAttrs,
    pub content: Vec<InlineNode>,
    pub children: Vec<BlockNode>,
}

pub enum BlockKind {
    Paragraph,
    Heading,
    BulletList,
    OrderedList,
    ListItem,
    Blockquote,
    CodeBlock,
    HorizontalRule,
}

pub struct BlockAttrs {
    pub level: Option<u8>,
    pub language: Option<String>,
    pub start: Option<u32>,
}

pub enum InlineNode {
    Text { text: String, marks: Vec<InlineMark> },
    HardBreak,
}

pub enum InlineMark {
    Bold,
    Italic,
    Strike,
    Code,
    Link { href: String },
}
```

约束：`schemaVersion = 1`；所有 block 使用全库唯一 UUID v4；至少一个空 paragraph 是合法文档；每文档最多 10,000 blocks、深度 32、JSON 10 MiB、单 text node 1 MiB；heading 仅 1–6；list 只能含 list item；链接只允许 `http`、`https`、`mailto`；WikiLink 仍是普通文本 `[[标题]]`。语义空文档只允许主窗新建和编辑器清空产生，快速捕获仍拒绝空白输入。

## 4. 数据库设计

### schema 005：块文档和投影

```sql
CREATE TABLE entry_documents (
  entry_id TEXT PRIMARY KEY REFERENCES entries(id) ON DELETE CASCADE,
  schema_version INTEGER NOT NULL CHECK (schema_version = 1),
  entry_revision INTEGER NOT NULL,
  source_content_checksum TEXT NOT NULL,
  document_json TEXT NOT NULL CHECK (json_valid(document_json)),
  markdown_text TEXT NOT NULL,
  plain_text TEXT NOT NULL,
  legacy_content TEXT NULL,
  updated_at TEXT NOT NULL
);

CREATE TABLE blocks (
  id TEXT PRIMARY KEY,
  entry_id TEXT NOT NULL REFERENCES entries(id) ON DELETE CASCADE,
  parent_block_id TEXT NULL REFERENCES blocks(id) ON DELETE CASCADE,
  ordinal INTEGER NOT NULL CHECK (ordinal >= 0),
  depth INTEGER NOT NULL CHECK (depth BETWEEN 0 AND 32),
  kind TEXT NOT NULL,
  text_content TEXT NOT NULL,
  attrs_json TEXT NOT NULL CHECK (json_valid(attrs_json))
);

CREATE INDEX idx_blocks_entry_parent_ordinal
  ON blocks(entry_id, parent_block_id, ordinal);
CREATE INDEX idx_blocks_entry_kind ON blocks(entry_id, kind);
```

005 的 SQL 只建结构。Rust data migration 在同一 transaction 中将旧 `current_content` 原样写入 `legacy_content`，按空行生成 paragraph blocks、单换行生成 `HardBreak`，不解释 Markdown 标记；写入 document 和投影后，不改旧 current content、revision、updated_at、WikiLink 或 FTS，并将 `entry_revision` 记为当时的 entry revision。

schema 005、DocumentsRepo 和 EntriesRepo 写路径切换是**同一内部发布单元**：任务 2–4 完成前禁止打包或推送可供用户安装的 alpha。005 记录 `source_content_checksum = checksum(current_content)`。任务 4 执行 repair：revision 不同且 checksum 也变化时，从最新 `current_content` 重建 document/projection；revision 不同但 checksum 相同表示只有元数据变化，只同步 `entry_revision`。repair 完成后才允许读取块文档，避免过期 document 覆盖新正文或无谓重生成 block ID。

### schema 006：文档父子层级

```sql
CREATE TABLE entry_hierarchy (
  entry_id TEXT PRIMARY KEY REFERENCES entries(id) ON DELETE CASCADE,
  parent_entry_id TEXT NULL REFERENCES entries(id) ON DELETE SET NULL,
  sibling_order INTEGER NOT NULL DEFAULT 0 CHECK (sibling_order >= 0),
  updated_at TEXT NOT NULL,
  CHECK (entry_id <> parent_entry_id)
);
CREATE INDEX idx_entry_hierarchy_parent_order
  ON entry_hierarchy(parent_entry_id, sibling_order, entry_id);
```

006 data migration 必须为全部既有、未删除的 knowledge entry 插入 root 行，初始 `sibling_order` 使用 `ROW_NUMBER() OVER (ORDER BY updated_at DESC, id ASC) - 1`（或等价 Rust 逐条编号）写入互异的 `0..n-1`。运行期不变量是“未删除 knowledge 必有且仅有一行，capture/trash 无行”；索引重建负责修复历史异常。

promote 插入 root 行；move 必须检查环、校验 expected revision 并重排 siblings；demote 只允许 root 且无 children，成功时必须删除该 entry 的 hierarchy 行。soft trash 时删除本条 hierarchy 行并把直接 children 提升为 root，restore 时以 root 恢复，不隐式复原旧 parent；永久删除沿用同样结果。以上变化与 entry revision 在同一事务内提交，revision 只增加一次。

### schema 007：导入来源

```sql
CREATE TABLE entry_imports (
  entry_id TEXT PRIMARY KEY REFERENCES entries(id) ON DELETE CASCADE,
  source_path TEXT NOT NULL,
  content_hash TEXT NOT NULL,
  imported_at TEXT NOT NULL,
  UNIQUE(source_path, content_hash)
);
CREATE INDEX idx_entry_imports_content_hash ON entry_imports(content_hash);
```

相同规范化路径和 hash 再导入时跳过；路径相同但内容变化时创建新 capture，不覆盖既有 entry。

## 8. 验收标准

### 数据正确性

- 0.3.0 所有 entry 都生成 schemaVersion 1 document；迁移不改变原 `current_content`、revision、updated_at。
- `legacy_content` 与迁移前 `current_content` 字节一致；仅打开、hydrate、切换条目不触发写回。
- 用户首次实际编辑旧条目后，`current_content` 可按规范 serializer 转为标准 Markdown；`legacy_content` 永远保留升级前字节，原始内容与 WikiLink 语义不得丢失。测试必须覆盖尾随空白、空行、单换行、Markdown 标记和 WikiLink。
- document、blocks、派生 Markdown、WikiLink、source checksum 和 revision 同事务提交或回滚。
- 删除 blocks 后可从 document JSON 完整重建，block ID 不变。
- 快速捕获草稿仍是纯文本，提交后生成有效 document。

### 编辑体验

- 支持段落、1–6 级标题、无序/有序列表、引用、代码块、分隔线、粗体、斜体、删除线、行内代码、链接、撤销重做。
- 不支持的粘贴内容降级为已定义节点，不执行脚本，不产生未知 schema。
- 自动保存、revision conflict、切换 flush 和保存失败状态与 0.3.0 语义一致。
- 500 blocks 文档可编辑，无明显输入延迟或布局跳动。

### 组织与发现

- knowledge entry 可形成单父树，不能成环；capture/trash 不能成为父节点。
- 面包屑和 outline 均从现有数据派生，不保存第二份导航结构。
- health 四类问题定义稳定、分页并可打开来源条目。

### 可移植性

- 2notes 自身导出文件可重新导入；已存在 frontmatter id 不覆盖原条目。
- 外部 Markdown 原文保存在 original content；结构解析 warning 可见。
- 导入失败按文件报告；成功项可搜索、编辑、导出和备份。

## 9. 明确非目标

- 0.4.0 不实现块级引用、块嵌入或锚文本更新，只保证稳定 block ID 和投影。
- 不实现图谱可视化、AI 写入、MCP、插件、云同步、多人协作或 CRDT。
- 不实现块拖拽、斜杠命令、表格、附件、公式、Mermaid、Canvas 或属性数据库。
- Markdown 导入是显式复制，不形成实时双主。
- 文档层级是单父树，不实现多父 / cloning。

## 10. 后续路线

### 0.5：块级引用

新增 `block_links(source_block_id, target_block_id)`；引用语法、锚文本、块删除和导出格式另写 ADR。先做精准反链和来源上下文，再考虑块嵌入。

### 0.6：可视化图谱

节点默认是 document，边来自 entry links；局部图优先。只有使用数据证明必要时才加入 block graph。

### 0.7：AI 只读接口

默认关闭，只读并按用户选择范围开放，不暴露 trash、draft、文件路径和设置。先定义威胁模型、审计日志、速率限制和可撤销授权，再决定 MCP 或应用内 API。

## 11. 风险与止损

| 风险 | 监测 | 止损 |
|---|---|---|
| Tiptap 绑定领域模型 | adapter 无法表达节点 | 保持 BlockDocument 子集，拒绝编辑器私有节点 |
| 迁移格式化旧内容 | current/legacy 字节比对失败 | 005 立即回滚，不启动主界面 |
| 三种表示漂移 | rebuild 报告不一致 | 禁止写入，从 document 重建 projection/Markdown |
| 大文档保存慢 | 100/500 blocks 超预算 | profile 后批量插入；仍失败则延后发布 |
| hierarchy 退化 | 10k tree 超 200ms | 单次平面查询 + 内存组树，不做递归 N+1 |
| 导入破坏数据 | hash/original 不一致 | 单文件 transaction 回滚并报告 |
| 范围膨胀 | 出现拖拽、表格、嵌入需求 | 移入 0.5+，不进入 0.4 branch |

## 12. 自检

- 规格覆盖：块模型、编辑器、主窗新建、文档层级、大纲、知识健康、Markdown 导入、升级、搜索、链接、导出、备份和长期路线均有任务。
- 类型一致：持久化统一使用 `BlockDocument`；Tiptap 类型只存在于 adapter；`currentContent` 只读兼容。
- 事务一致：entry、document、projection、derived Markdown、tags、links 和 revision 归同一 transaction。
- 非目标一致：块级引用、图谱和 AI 明确进入后续版本，不与 0.4.0 混做。
- 每项实现均列出文件、接口、失败测试、验证命令、预期结果和提交边界。
